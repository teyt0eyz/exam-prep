Semantic Versioning (SemVer)

หมายเหตุจากเอกสาร

Scope 2026A ข้อ 14 คือ "Semantic Versioning" ไม่มีสไลด์ในโฟลเดอร์ บทนี้เป็น เนื้อหาเสริม ตามมาตรฐาน semver.org และกฎช่วงเวอร์ชันของ npm

นึกภาพก่อน

เลขเวอร์ชัน 4.19.2 ไม่ใช่แค่ตัวเลขเรียงกัน แต่เป็น สัญญา จากผู้เขียน library ว่าการอัปเดตแต่ละแบบจะกระทบโค้ดของเราแค่ไหน ถ้าทุกคนรักษาสัญญานี้ npm ก็อัปเดตให้อัตโนมัติได้อย่างปลอดภัย

MAJOR.MINOR.PATCH

text
   4  .  19  .  2
   │      │     └── PATCH: แก้ bug โดยไม่เปลี่ยน API
   │      └──────── MINOR: เพิ่มความสามารถใหม่ ที่ยังเข้ากันได้กับของเดิม
   └─────────────── MAJOR: เปลี่ยนแบบ "ไม่เข้ากันกับของเดิม" (breaking change)
ขึ้นเลขเมื่อตัวอย่างโค้ดเดิมยังใช้ได้ไหม
PATCHแก้ bug, แก้ช่องโหว่ โดย API เหมือนเดิม4.19.2 → 4.19.3ได้
MINORเพิ่ม function / option ใหม่ (ของเก่ายังอยู่) หรือประกาศว่าจะเลิกใช้ (deprecate)4.19.2 → 4.20.0ได้
MAJORลบหรือเปลี่ยนชื่อ function, เปลี่ยนพฤติกรรม, เลิกรองรับ Node เวอร์ชันเก่า4.19.2 → 5.0.0อาจไม่ได้ ต้องอ่าน migration guide

กฎการรีเซ็ต

เมื่อขึ้นเลขตำแหน่งใด เลขทางขวาทั้งหมดกลับเป็น 0:

  • 1.4.7 + MINOR → 1.5.0 (ไม่ใช่ 1.5.7)
  • 1.4.7 + MAJOR → 2.0.0
  • เลขแต่ละตำแหน่ง ไม่ใช่ทศนิยม: 1.10.0 ใหม่กว่า 1.9.0 (10 > 9)

เวอร์ชัน 0.x.y

0.y.z หมายถึง ยังอยู่ระหว่างพัฒนา API อาจเปลี่ยนได้ทุกเมื่อ เวอร์ชัน 1.0.0 คือการประกาศ API สาธารณะที่มั่นคงครั้งแรก

Pre-release และ build metadata

รูปแบบความหมาย
2.0.0-alpha.1ทดลองช่วงแรก ยังไม่ครบ
2.0.0-beta.3ครบแล้ว กำลังทดสอบ
2.0.0-rc.1release candidate ใกล้ปล่อยจริง
2.0.0+build.45build metadata ไม่มีผลต่อลำดับเวอร์ชัน

ลำดับ: 2.0.0-alpha.1 < 2.0.0-beta.1 < 2.0.0-rc.1 < 2.0.0 — pre-release มาก่อน เวอร์ชันจริงเสมอ

ช่วงเวอร์ชันใน package.json

1.4.7ตรงตัวเท่านั้น1.4.7ไม่อัปเดต
^1.4.7 (caret, ค่าเริ่มต้นของ npm install)>=1.4.7 <2.0.01.4.8, 1.5.0, 1.9.9 ✓ · 2.0.0 ✗MINOR + PATCH
~1.4.7 (tilde)>=1.4.7 <1.5.01.4.8, 1.4.99 ✓ · 1.5.0 ✗PATCH เท่านั้น

* หรือ "latest"อะไรก็ได้ / ล่าสุด—ทุกอย่าง (เสี่ยงที่สุด)

caret กับเวอร์ชัน 0.x

caret ไม่ยอมเปลี่ยนเลขซ้ายสุดที่ไม่ใช่ศูนย์:

เขียนยอมรับ
^1.2.3>=1.2.3 <2.0.0
^0.2.3>=0.2.3 <0.3.0 (เพราะเลข 0.x ถือว่า MINOR อาจ breaking)
^0.0.3>=0.0.3 <0.0.4 (ตรงตัว)

เวอร์ชันใดถูกติดตั้ง

  • npm install express ติดตั้งเวอร์ชันล่าสุด และบันทึกเป็น "express": "^4.21.1" (สมมติล่าสุดคือ 4.21.1)
  • npm install ภายหลังจะติดตั้ง ตาม package-lock.json ถ้ามี ไม่ใช่เวอร์ชันล่าสุดในช่วง
  • npm update อัปเดตให้เป็นเวอร์ชันล่าสุด ภายในช่วง ที่ package.json อนุญาต แล้วแก้ lock
  • ข้าม MAJOR ต้องสั่งเอง: npm install express@5

ตัวอย่างไล่ทีละขั้น

package.json มี "lodash": "^4.17.15", "dayjs": "~1.11.7", "chalk": "4.1.2" และใน registry มีเวอร์ชัน: lodash: 4.17.21, 5.0.0 · dayjs: 1.11.13, 1.12.0 · chalk: 4.1.2, 5.3.0

packageช่วงที่ยอมรับnpm update ได้
lodash ^4.17.15>=4.17.15 <5.0.04.17.21 (5.0.0 เกินช่วง)
dayjs ~1.11.7>=1.11.7 <1.12.01.11.13 (1.12.0 เกินช่วง)
chalk 4.1.2ตรงตัว4.1.2 (ไม่เปลี่ยน)

จุดที่มักพลาด

  • สลับ ^ กับ ~ — ^ = minor + patch (คง MAJOR) · ~ = patch (คง MAJOR.MINOR)
  • ลืมรีเซ็ตเลขทางขวา (1.4.7 + minor ≠ 1.5.7)
  • อ่าน 1.10.0 ว่าน้อยกว่า 1.9.0
  • คิดว่าเพิ่มฟีเจอร์ใหม่ต้องขึ้น MAJOR — ถ้าเข้ากันได้กับของเดิม ขึ้น MINOR
  • คิดว่าแก้ bug ที่ทำให้พฤติกรรมเปลี่ยนจนโค้ดผู้ใช้พังเป็นแค่ PATCH — ถ้าไม่เข้ากันกับของเดิม ต้อง MAJOR
  • คิดว่า 2.0.0-beta.1 ใหม่กว่า 2.0.0
  • ลืมว่า caret กับ 0.x แคบกว่าปกติ

สรุปก่อนสอบ

  • MAJOR.MINOR.PATCH · MAJOR = breaking change · MINOR = ฟีเจอร์ใหม่ที่เข้ากันได้ · PATCH = แก้ bug
  • ขึ้นเลขตำแหน่งใด เลขทางขวากลับเป็น 0 · เทียบเป็นจำนวนเต็ม (1.10.0 > 1.9.0)
  • 0.y.z = ยังพัฒนา API ไม่มั่นคง · 1.0.0 = API สาธารณะแรก
  • Pre-release: alpha < beta < rc < เวอร์ชันจริง
  • ^1.4.7 = >=1.4.7 <2.0.0 (ค่าเริ่มต้นของ npm) · ~1.4.7 = >=1.4.7 <1.5.0 · 1.4.7 = ตรงตัว · * = อะไรก็ได้
  • ^0.2.3 = <0.3.0 · ^0.0.3 = ตรงตัว
  • npm update อัปเดตภายในช่วง · ข้าม MAJOR ต้อง npm install pkg@5
