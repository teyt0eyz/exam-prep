## นึกภาพก่อน

ธนาคารแห่งหนึ่งมีตารางยอดโอนเงิน รูปถ่ายใบหน้าลูกค้า และไฟล์เสียงจาก Call Center ทั้งสามอย่างเป็น "ข้อมูล" แต่วิเคราะห์ด้วยวิธีเดียวกันไม่ได้
ก่อนวิเคราะห์จึงต้องตอบให้ได้ก่อนว่าข้อมูลตรงหน้าเป็นประเภทใด

## ทำไมต้องรู้จักประเภทของข้อมูลก่อน

- เพื่อ **แยกแยะ** ข้อมูลประเภทต่าง ๆ ได้
- การแบ่งมีหลายแบบ: ตาม **โครงสร้าง (Structure)**, ตาม **ความเป็นเจ้าของ (Data Owner)** และตาม **คุณลักษณะทางสถิติ**
- การวิเคราะห์ข้อมูลเกี่ยวข้องกับสถิติพื้นฐาน เมื่อแยกประเภทได้จึง **เลือกวิธีทางสถิติที่เหมาะสม** ได้

## แบ่งตามโครงสร้าง

| | **Structured Data** | **Unstructured Data** |
|---|---|---|
| การแสดงผล | แสดงเป็น rows, columns และ relational database **ได้** | แสดงเป็น rows, columns **ไม่ได้** |
| ตัวอย่าง | ตัวเลข วันที่ ข้อความ (numbers, dates, strings) | รูปภาพ เสียง วิดีโอ ไฟล์เอกสาร อีเมล |
| สัดส่วนในองค์กร (Gartner) | ประมาณ **20%** | ประมาณ **80%** |
| พื้นที่จัดเก็บ | ใช้ **น้อยกว่า** | ใช้ **มากกว่า** |
| การจัดการและป้องกัน | **ง่ายกว่า** ด้วยเครื่องมือเดิม | **ยากกว่า** |

<DocNote>

ตารางเปรียบเทียบในสไลด์ (อ้าง Gartner) ใส่ "spreadsheets" ไว้ฝั่ง Unstructured ร่วมกับ word processing files และ e-mail
แต่แบบทดสอบในสไลด์เดียวกันจัดข้อมูลที่อยู่ในตาราง (ยอดเงินโอน, จำนวนสินค้าที่ขายได้, สินค้าคงคลังใน Database) เป็น **Structured** ทั้งหมด ข้อสอบในเว็บนี้ยึดตามแบบทดสอบ: ข้อมูลที่จัดเป็นแถวและคอลัมน์ได้คือ Structured

</DocNote>

## แบ่งตามความเป็นเจ้าของ (Data Owner)

| ประเภท | ที่มา | ตัวอย่างในสไลด์ |
|---|---|---|
| **1st Party Data** | บริษัทเก็บเองโดยตรงจากลูกค้าของตัวเอง | ข้อมูลฝากถอนเงินของลูกค้า, ข้อมูลสมัคร Member, Transactions ที่ลูกค้าซื้อสินค้า |
| **2nd Party Data** | ข้อมูลของบริษัท **Partner** ที่แบ่งปันกัน | ข้อมูลจาก Platform ส่งของ (Delivery) ที่เป็น Partner, ข้อมูลผู้ให้บริการมือถือที่เป็น Partner |
| **3rd Party Data** | ข้อมูลที่รวบรวมจากคนจำนวนมากโดยผู้อื่น | ข้อมูล Social Media ทั่วไป |

เปรียบเทียบ **คุณภาพ (Quality)** กับ **การเข้าถึงผู้คน (Reach)**:

| | Quality | Reach |
|---|---|---|
| 1st Party | **สูงสุด** | ต่ำสุด |
| 2nd Party | กลาง | กลาง |
| 3rd Party | ต่ำสุด | **สูงสุด** |

ยิ่งเป็นข้อมูลของเราเอง ยิ่งแม่นแต่ครอบคลุมคนได้น้อย ยิ่งเป็นข้อมูลจากภายนอก ยิ่งครอบคลุมคนมากแต่คุณภาพลดลง

## แบ่งตามวิธีการทางสถิติ

| กลุ่มใหญ่ | กลุ่มย่อย | ตัวอย่างในสไลด์ |
|---|---|---|
| **Numerical Data** (Quantitative) | **Discrete Data** (นับเป็นจำนวนเต็ม) | จำนวนลูกค้า, จำนวนสินค้า |
| | **Continuous Data** (ค่าต่อเนื่อง) | ยอดขาย, ภาษีมูลค่าเพิ่ม |
| **Categorical Data** (Qualitative) | **Nominal Data** (ไม่มีลำดับ) | เพศ, สัญชาติ |
| | **Ordinal Data** (มีลำดับ) | คะแนนความพึงพอใจที่สำรวจจากลูกค้า |

จากแบบทดสอบในสไลด์:

- คอลัมน์ **Age** → Numerical · คอลัมน์ **Occupation** → Categorical
- คอลัมน์ **Branch** → Categorical · คอลัมน์ **Gross income** → Numerical

## ตัวอย่างข้อมูลในธุรกิจ

| ชนิด | คอลัมน์ตัวอย่าง |
|---|---|
| **Transactional Data** | Sales Transaction, Products, Category, Order ID, Customer ID |
| **Customer Data** | Name, E-mail, Age, Gender, Income, Occupation, Address, Customer ID |
| **Payment Data** | Paid Date, Paid Amount, Payment ID, Customer ID |
| **Campaign Data** | Campaign Code, Campaign Response, Customer ID |
| **Call Center Data** | Reason to Call, Duration, Call Recorded, Call ID, Agent ID, Customer ID |

### แบบทดสอบในสไลด์: ดูตารางแล้วบอกชนิด

| ตารางมีคอลัมน์ | ชนิด |
|---|---|
| Customer ID, Age, Education, Marital status, Occupation, Race, Sex, Native-country, Salary | **Demographic Data** (ลักษณะของตัวบุคคล) |
| Account No, DATE, TRANSACTION DETAILS, WITHDRAWAL AMT, DEPOSIT AMT, BALANCE AMT | **Transactional Data** (รายการที่เกิดขึ้นแต่ละครั้ง) |
| Invoice ID, Branch, Customer type, Product, Unit price, Quantity, Total, Payment | **Invoice Data** |
| CATEGORY_NAME, PRODUCT_NAME, LIST_PRICE, WAREHOUSE, QUANTITY | **Inventory Data** (สินค้าคงคลัง) |

วิธีแยก: Demographic บอกว่า **"คนนี้เป็นใคร"** ส่วน Transactional บอกว่า **"เกิดอะไรขึ้น เมื่อไร เท่าไร"**

ทุกตารางมี **Customer ID** ร่วมกัน จึงเชื่อมข้อมูลข้ามตารางได้ การจัดเก็บใน Database แสดงความสัมพันธ์ด้วย **ER Diagram** (ER ย่อจาก **Entity Relationship**)

## นำข้อมูลไปใช้ประโยชน์

- สร้าง **Report หรือ Dashboard** เพื่อติดตาม **KPI (Key Performance Index)** เช่น ยอดขาย กำไร สินค้าคงคลัง สินค้าระหว่างจัดส่ง
- **วิเคราะห์สถานะธุรกิจ**: สินค้าใดขายดี สาขาไหนยอดขายดีที่สุด แต่ละช่วงเวลายอดขายต่างกันหรือไม่
- สร้าง **AI หรือ Machine Learning** เพื่อทำนาย เช่น ลูกค้าคนใดจะ **Churn**, ใครจะตอบรับแคมเปญ, แต่ละคนจะสร้างรายได้เท่าไร (**CLTV**)

## ข้อมูลส่วนบุคคลและ PDPA

หลักการเก็บข้อมูลส่วนบุคคล 5 ข้อ:

1. ห้ามเก็บโดย **ไม่ได้รับความยินยอม** (ต้องขอ **Consent**)
2. ห้ามเก็บ **เกินความจำเป็น**
3. ต้อง **บอกวัตถุประสงค์** ในการเก็บ
4. หาก **เปลี่ยนวัตถุประสงค์** ต้องแจ้งเจ้าของข้อมูลให้ทราบ
5. ห้ามเก็บจากแหล่งอื่น ต้อง **เก็บโดยตรงจากเจ้าของข้อมูล**

เพื่อลดโอกาสที่ข้อมูลส่วนบุคคลรั่วไหล บริษัทจะสร้าง **Customer ID** ไว้อ้างอิงภายใน ผู้ที่ไม่เกี่ยวข้องจึงไม่เห็นข้อมูลส่วนบุคคลของลูกค้า

## ตัวอย่างไล่ทีละขั้น

ธุรกิจค้าปลีกแห่งหนึ่ง (แบบทดสอบในสไลด์):

| ข้อมูล | Structured? | เหตุผล |
|---|---|---|
| วิดีโอ CCTV ที่ใช้นับลูกค้าเข้าออกร้าน | **Unstructured** | เป็นวิดีโอ จัดเป็นแถวและคอลัมน์ไม่ได้ |
| สินค้าคงคลังที่เก็บใน Database (DBMS) | **Structured** | อยู่ในตารางของ database |
| จำนวนสินค้าที่ขายได้ เพื่อสรุปรายได้แต่ละวัน | **Structured** | เป็นตัวเลขในตาราง |

| ข้อมูล | เจ้าของ | เหตุผล |
|---|---|---|
| ข้อมูลผู้ให้บริการมือถือที่เป็น Partner (บอก Location ลูกค้า) | **Second Party** | เป็นข้อมูลของ Partner |
| ข้อมูลที่ลูกค้าสมัคร Member กับร้านในเครือ | **First Party** | ร้านเก็บเองจากลูกค้าโดยตรง |
| Transactions ที่ลูกค้าซื้อสินค้าจากร้านในเครือ | **First Party** | เกิดในระบบของร้านเอง |

## จุดที่มักพลาด

- เห็นตัวเลขแล้วตอบ Numerical ทันที — คะแนนความพึงพอใจ 1–5 ในสไลด์จัดเป็น **Ordinal (Categorical)** เพราะเป็นระดับที่มีลำดับ
- สลับ 20% กับ 80% — ข้อมูลส่วนใหญ่ขององค์กร (80%) เป็น **Unstructured**
- คิดว่า 3rd Party คุณภาพดีที่สุดเพราะข้อมูลเยอะ — 3rd Party มี Reach สูงสุด แต่ **Quality ต่ำสุด**
- สับสน 2nd กับ 3rd Party — คำว่า **Partner** คือ 2nd Party
- คิดว่าเก็บข้อมูลส่วนบุคคลจากแหล่งอื่นได้ถ้าเปิดเผยอยู่แล้ว — ต้องเก็บโดยตรงจากเจ้าของข้อมูลและได้รับ Consent
