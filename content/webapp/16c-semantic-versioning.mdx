## นึกภาพก่อน

เลขเวอร์ชัน `4.19.2` ไม่ใช่แค่ตัวเลขเรียงกัน แต่เป็น **สัญญา** จากผู้เขียน library ว่าการอัปเดตแต่ละแบบจะกระทบโค้ดของเราแค่ไหน
ถ้าทุกคนรักษาสัญญานี้ npm ก็อัปเดตให้อัตโนมัติได้อย่างปลอดภัย

## MAJOR.MINOR.PATCH

```text
   4  .  19  .  2
   │      │     └── PATCH: แก้ bug โดยไม่เปลี่ยน API
   │      └──────── MINOR: เพิ่มความสามารถใหม่ ที่ยังเข้ากันได้กับของเดิม
   └─────────────── MAJOR: เปลี่ยนแบบ "ไม่เข้ากันกับของเดิม" (breaking change)
```

| ขึ้นเลข | เมื่อ | ตัวอย่าง | โค้ดเดิมยังใช้ได้ไหม |
|---|---|---|---|
| **PATCH** | แก้ bug, แก้ช่องโหว่ โดย API เหมือนเดิม | `4.19.2` → `4.19.3` | **ได้** |
| **MINOR** | เพิ่ม function / option ใหม่ (ของเก่ายังอยู่) หรือประกาศว่าจะเลิกใช้ (deprecate) | `4.19.2` → `4.20.0` | **ได้** |
| **MAJOR** | ลบหรือเปลี่ยนชื่อ function, เปลี่ยนพฤติกรรม, เลิกรองรับ Node เวอร์ชันเก่า | `4.19.2` → `5.0.0` | **อาจไม่ได้** ต้องอ่าน migration guide |

### กฎการรีเซ็ต

เมื่อขึ้นเลขตำแหน่งใด **เลขทางขวาทั้งหมดกลับเป็น 0**:

- `1.4.7` + MINOR → **`1.5.0`** (ไม่ใช่ 1.5.7)
- `1.4.7` + MAJOR → **`2.0.0`**
- เลขแต่ละตำแหน่ง **ไม่ใช่ทศนิยม**: `1.10.0` **ใหม่กว่า** `1.9.0` (10 > 9)

### เวอร์ชัน 0.x.y

**`0.y.z`** หมายถึง **ยังอยู่ระหว่างพัฒนา** API อาจเปลี่ยนได้ทุกเมื่อ เวอร์ชัน **`1.0.0`** คือการประกาศ API สาธารณะที่มั่นคงครั้งแรก

### Pre-release และ build metadata

| รูปแบบ | ความหมาย |
|---|---|
| `2.0.0-alpha.1` | ทดลองช่วงแรก ยังไม่ครบ |
| `2.0.0-beta.3` | ครบแล้ว กำลังทดสอบ |
| `2.0.0-rc.1` | **release candidate** ใกล้ปล่อยจริง |
| `2.0.0+build.45` | build metadata ไม่มีผลต่อลำดับเวอร์ชัน |

ลำดับ: `2.0.0-alpha.1` < `2.0.0-beta.1` < `2.0.0-rc.1` < **`2.0.0`** — pre-release **มาก่อน** เวอร์ชันจริงเสมอ

## ช่วงเวอร์ชันใน package.json

| เขียน | ยอมรับ | ตัวอย่างกับ `1.4.7` | อัปเดตอะไรได้ |
|---|---|---|---|
| `1.4.7` | **ตรงตัวเท่านั้น** | `1.4.7` | ไม่อัปเดต |
| **`^1.4.7`** (caret, **ค่าเริ่มต้นของ npm install**) | `>=1.4.7 <2.0.0` | `1.4.8`, `1.5.0`, `1.9.9` ✓ · `2.0.0` ✗ | **MINOR + PATCH** |
| **`~1.4.7`** (tilde) | `>=1.4.7 <1.5.0` | `1.4.8`, `1.4.99` ✓ · `1.5.0` ✗ | **PATCH เท่านั้น** |
| `>=1.4.7` | 1.4.7 ขึ้นไปทั้งหมด | รวม `2.0.0`, `3.0.0` | ทุกอย่าง (เสี่ยง) |
| `*` หรือ `"latest"` | อะไรก็ได้ / ล่าสุด | — | ทุกอย่าง (เสี่ยงที่สุด) |

### caret กับเวอร์ชัน 0.x

caret **ไม่ยอมเปลี่ยนเลขซ้ายสุดที่ไม่ใช่ศูนย์**:

| เขียน | ยอมรับ |
|---|---|
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.2.3` | `>=0.2.3 <0.3.0` (เพราะเลข 0.x ถือว่า MINOR อาจ breaking) |
| `^0.0.3` | `>=0.0.3 <0.0.4` (ตรงตัว) |

## เวอร์ชันใดถูกติดตั้ง

- `npm install express` ติดตั้งเวอร์ชันล่าสุด และบันทึกเป็น `"express": "^4.21.1"` (สมมติล่าสุดคือ 4.21.1)
- `npm install` ภายหลังจะติดตั้ง **ตาม `package-lock.json`** ถ้ามี ไม่ใช่เวอร์ชันล่าสุดในช่วง
- `npm update` อัปเดตให้เป็นเวอร์ชันล่าสุด **ภายในช่วง** ที่ package.json อนุญาต แล้วแก้ lock
- ข้าม MAJOR ต้องสั่งเอง: `npm install express@5`

## ตัวอย่างไล่ทีละขั้น

package.json มี `"lodash": "^4.17.15"`, `"dayjs": "~1.11.7"`, `"chalk": "4.1.2"` และใน registry มีเวอร์ชัน:
lodash: 4.17.21, 5.0.0 · dayjs: 1.11.13, 1.12.0 · chalk: 4.1.2, 5.3.0

| package | ช่วงที่ยอมรับ | `npm update` ได้ |
|---|---|---|
| lodash `^4.17.15` | `>=4.17.15 <5.0.0` | **4.17.21** (5.0.0 เกินช่วง) |
| dayjs `~1.11.7` | `>=1.11.7 <1.12.0` | **1.11.13** (1.12.0 เกินช่วง) |
| chalk `4.1.2` | ตรงตัว | **4.1.2** (ไม่เปลี่ยน) |

## จุดที่มักพลาด

- สลับ `^` กับ `~` — **^ = minor + patch** (คง MAJOR) · **~ = patch** (คง MAJOR.MINOR)
- ลืมรีเซ็ตเลขทางขวา (`1.4.7` + minor ≠ `1.5.7`)
- อ่าน `1.10.0` ว่าน้อยกว่า `1.9.0`
- คิดว่าเพิ่มฟีเจอร์ใหม่ต้องขึ้น MAJOR — ถ้าเข้ากันได้กับของเดิม ขึ้น MINOR
- คิดว่าแก้ bug ที่ทำให้พฤติกรรมเปลี่ยนจนโค้ดผู้ใช้พังเป็นแค่ PATCH — ถ้าไม่เข้ากันกับของเดิม ต้อง MAJOR
- คิดว่า `2.0.0-beta.1` ใหม่กว่า `2.0.0`
- ลืมว่า caret กับ `0.x` แคบกว่าปกติ
